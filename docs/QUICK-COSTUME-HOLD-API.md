# Quick booking costume hold — owner walkthrough item 3 (proposal)

2026-10-20 · Codex · contract before implementation. Owner wants the selected character's physical costume and exact selected wardrobe held when recording the booking deposit. Staff/equipment/transport assignment remains later. This document proposes the lifecycle for Claude review; **no hold backend, route, migration, reservation or cancellation implemented by this proposal**.

## Meaning and source of inventory truth

A costume-only hold is a real inventory commitment, not `capacity_reserved`, staff acceptance or a whole-party availability guarantee. Keep event draft, label “Traje apartado; personal y traslados por confirmar”. Match compiled EventService costume slots only, never reserve another person. A selected wig character without a physical costume requirement creates no fake costume. An incomplete required character selection is explicit `needs_character` and creates no new hold until that recipe is complete; the already recorded deposit remains. No invented character/outfit and no claim that a partly specified recipe is fully held. This conservative missing-choice behavior is part of the proposal for Claude review.

Use existing `resource_reservations`, linked through a new auditable hold registry to QuickBookingRecord and its real verified test deposit receipt. Scheduler/blocks/resource editing must see holds immediately. Hold registry freezes unit id/version, character id/version, requested/chosen wardrobe including literal"0", normalized event timing and source receipt, plus version/state and lifecycle history. It must not redefine the frozen V1 reservation/evidence schemas or append fake BookingEvidence/payment entries. Existing confirmed parties are not retroactively changed.

## Booking money and allocation

**Never lose a real recorded deposit because no costume can be held.** QuickBook first commits its existing idempotent customer/event/finance/actual receipt core; a separate serialized hold attempt records held/blocked/incomplete afterward. Hold failure returns the committed booking and a plain warning, not a false whole-booking rollback. All required costume units in one attempt reserve atomically or none; no partial silent fulfillment. Existing short-notice/deposit-exception/staff/driver review still applies at final confirmation. No new commercial deposit threshold or automatic expiration policy is invented.

Proposed internal `HoldQuickBookingCostumes::execute(User $actor,int $quickBookingId,array $input,string $key):array` accepts displayed event version and selected character versions, plus optional owner-selected unit/version pins; no client-computed availability. Deterministic matching across available active units uses the full shared costume matching policy (fixed vs generic wardrobe, maximum matching rather than greedy). It cannot silently replace an exact outfit, nor consume the same head twice. No generic wardrobe preselected when none was requested. Unit choice is an inventory allocation; interpreter compatibility is checked later with staff.

Lock owner→event→sorted characters→sorted candidate units before current reservation/block reads. Check [event start−setup,event end+breakdown), both buffers known, against all existing confirmed/held reservations and active blocks; exclude only this same hold/event's owned rows when rechecking. Resource and character versions/current state are revalidated under locks. Concurrent requests for the last unit cannot both succeed; all failures retain the actual receipt. No release/reallocation performed from GET or ordinary exact core replay. Exact attempt UUID/body returns its recorded outcome; an owner retry of a blocked attempt is a new deliberate intent. Provider/DB failure never yields a claim that a hold succeeded.

Conflict message: “No se pudo apartar el traje de {personaje}[ ({vestuario})] para ese horario. El depósito quedó registrado. Revisa otra unidad, horario o personaje; aún no está confirmada la capacidad.” Owner-only names, no other client's identity. Closed issue codes: `needs_character`, `timing_required`, `costume_unavailable`, `costume_catalog_changed`, `hold_review_required`.

## Final assignment, editing and release (required together before enabling)

Final ConfirmCapacity/ConfirmPaidCapacity/ConfirmImportedCapacity must account for existing held rows: include/pin these exact units and wardrobe choices, exclude only their owned reservations from self-conflict, recheck the whole operational match and all adjacent transfers, then **promote/consume** the holds and retain one reservation per event/unit atomically. Failure keeps all original holds. No duplicate reservation, changing outfit by replay, or selecting a different unit while leaving the original locked. Staff week still shows confirmed events only.

SaveEventDraft/ApproveClientDetails and catalog/resource/block writes must preserve the commitment: permitted contact/address corrections do not change its character/outfit/time/units; schedule/service/buffer changes require a separate atomic hold replacement/release action and stale version refusal. A new address does not certify the unresolved transfer; final operational review remains mandatory. Never delete active held reservations during a draft recipe rebuild. Missing/corrupt registry or externally changed reservation requires review rather than a guessed new hold.

Cancellation must release **only this hold's** inventory in the same authorized cancellation transaction, with audit/history preserved, no fake money refund. No current CHANGE-A cancellation backend exists; do not claim the hook is active. Before enabling holds, provide the reviewed release/cancel integration and explicit owner release action with event/hold versions, reason and idempotency; no implicit expiry, lease duration or release from a browser refresh. A standalone owner release is an inventory decision, not a cancellation or deletion of the recorded deposit. Full cancellation policy stays in CHANGE-A.

Proposed read model in QuickBooking/owner event: `costume_hold:{state:not_required|needs_character|timing_required|blocked|held|consumed|released|review_required,version,rows:[{resource_id,resource_version,character_id,character_version,character_name,outfit}],issues,staff_confirmed:false}`. No names/phones of other clients/staff. Fields/routes remain **unregistered until exact attempt/release/final-confirm input and receipt semantics plus required tests are frozen**. Claude may review labels/state now, but no executable buttons against a fictional endpoint.

Tests required before delivery: actual deposit retained after inventory conflict/storage failure; exact body retry/no duplicate core or holds; real two-owner last-head race; generic/fixed outfit and literal0, multiple slots/maximum matching; setup/breakdown/block overlap; all final-confirm paths without self-conflict/duplicate rows and failed staffing preserves hold; draft/client-details edit boundaries; explicit release/retry and cancellation hook; resource/block/catalog mutation guards; privacy and immutable/audit/transaction failures. Synthetic records only. No real inventory reservation/import/deployment, sends, charges or HoneyBook modification.

## Executable V1 freeze — 2026-10-20, before code (Claude7a4cd10 amendment)

This section supersedes the proposal's unknown-buffer refusal. Missing setup/breakdown **does not prevent holding**: use party time extended only by known buffers; retain null in evidence, return `review_required` + `timing_unknown` with real held rows. Never call it full capacity or invent minutes. No lease/automatic expiry. Resolving null buffers may atomically expand the same hold after collision recheck; a failed expansion preserves the old event/window/hold. Changing known buffers, party times or compiled recipe requires owner release/retry first. Address/contact approval alone preserves the hold; no transfer availability is certified.

Owner services (finance + documents sandbox, owner2FA, staging HTTPS, no-store/private):

- `ReadQuickBookingCostumeHold::execute(User $actor,int $eventId):array`; GET `/admin/api/events/{event}/costume-hold`.
- `HoldQuickBookingCostumes::execute(User $actor,int $eventId,array $input,string $key):array`; POST same path. Closed input `{expected_event_version:int,expected_hold_version:int>=0,characters:[{id,version}]}`. The read supplies the exact character set and versions. Auto assignment chooses active physical units via maximum matching, no browser availability promise or arbitrary chosen resource. Missing character choices → needs_character/no rows. No physical costume slots → not_required.
- `ReleaseQuickBookingCostumes::execute(User $actor,int $eventId,array $input,string $key):array`; POST `/admin/api/events/{event}/costume-hold/release`. Closed input `{expected_event_version,expected_hold_version,reason:string10..1000}`. Draft only; consumed confirmed inventory cannot be released through this action. Releases only owned hold reservations, preserves deposit/booking/history; does not cancel the party or refund money.

Response `{event_id,event_version,version,state,issues,rows:[{resource_id,resource_version,character_id,character_version,character_name,outfit,reservation_id}],characters:[{id,version}],staff_confirmed:false}`. `not_attempted`/version0 when absent; blocked/needs_character/not_required/released have no held rows. `review_required` with timing_unknown has rows; `review_required` + integrity_invalid/hold_unavailable makes no current inventory claim. ## Owner screen wiring — executable V1 UI contract (before code)

A shared QuickCostumeHoldPanel Livewire component uses the existing read/attempt/release services directly, with an enrolled owner explicitly checked on mount, every action and render. It shows only the read model, not another party's reservations, receipt reference or staff contact. eventId, displayed hold/character/event versions, attempt/release UUIDs and an in-flight release snapshot are Locked server state. UI hides actions that cannot apply, but services remain the authority.

Show real held rows and wardrobe0; distinguish unknown timing, unavailable inventory, incomplete choices, integrity/storage review, consumed and released. Always state that personnel/equipment/transport confirmation is separate. Refresh only reloads the view and resets an explicitly abandoned attempt; never reserves or releases. Retry sends exactly the displayed pins and stable UUID, never fetches newer versions immediately before writing. Release requires its own owner-written10..1000-character reason and an explicit confirmation; freeze the valid reason/pins once per intent so a lost-response retry cannot release a later hold or change its evidence. Success updates the displayed read; a stale conflict asks for deliberate refresh/review. Generic unexpected errors retain the existing deposit and do not disclose SQL/provider text.

Embed the component after a saved QuickBook result and on its owner event page when a genuine QuickBookingRecord exists. No new HTTP API, staff confirmation, cancellation, refund, TTL or paid-hold renewal is introduced. Tests exercise actual read/attempt/release, locked-state tampering, stale displayed pins, literal wardrobe0, release reason validation and preserved receipts/other reservations, plus both page embeddings. Keep this paid flow separate from future unpaid48h Stripe backing.
