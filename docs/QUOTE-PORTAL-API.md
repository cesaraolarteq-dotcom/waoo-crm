# QUOTE-01 B/C: private presentation, acceptance and financial binding

2026-10-17 · Codex. Extends QUOTE-01-API.md (A source88d53f3), published before this implementation. No live messages, providers, prices or deployment authorized. Acceptance wording remains owner-configured/approved; draft email text is not approval of quote consent.

## B: prepare, review, accept

- `SendQuote::execute(User $actor,int $quoteId,array $input,string $key): array`; `POST /admin/api/quotes/{quote}/send`. Required `expected_version`, `expected_revision`; UUID key. Returns `{quote, presentation_id, portal_grant_id, url, expires_at}`. Client GET exposes separate accepted/rejected consent text/hash under one frozen version; decision input hash must match its route outcome. “Send” prepares a link only; never marks delivery. First presentation of a revision freezes a whitelist client snapshot, its canonical SHA-256, private PDF bytes/hash, locale and configured consent version/text/hash. Re-preparing uses that same immutable presentation. Active unrevoked links are not silently rotated; replay returns the same grant/link if still active, otherwise a safe inactive error. An explicit new-key prepare can issue a replacement for a revoked link without changing offer validity or presentation.
- Requires owner/fresh confirmed2FA, local/testing/staging + sandbox_quotes/finance/documents; staging link operations require HTTPS/secure session cookies. The approved `waoo.quote_acceptance_consent` config is empty by default (shape: version, es/en maps each containing accepted/rejected text; reject wording must record rejection rather than agreement); preparation fails422 until version/es/en texts are explicitly configured. Tests use fictional consent only. No default legal copy is activated.
- New immutable `quote_presentations` (unique revision), `quote_decisions` (unique quote/revision, outcome accepted|rejected, signer identity, trusted request IP/UA/time, grant, snapshot/PDF/consent hashes/text), `quote_pdf_views` (grant+presentation unique). New nullable portal_grants.quote_revision_id FK restrict. New quote token binding includes that ID as codec version2; old event tokens retain version1 exactly. Generic IssuePortalGrant cannot request quote scopes; only preparation issues exactly quote.read/quote.accept. Existing contract/payment/details grants never gain access to quotes; quote grants cannot read those event surfaces.
- Existing POST /portal/api/session handles the fragment token. `GET /portal/api/quote` derives identity/revision from the scoped session; returns whitelisted presentation payload, hashes, consent, persisted state and can_decide. No owner note, raw route evidence, recipes, internal discount reason, approval actor, phone/email list or audit request metadata is exposed. An accepted quote does not expire as an agreement; its access token still expires normally.
- `GET /portal/api/quote/pdf` serves only the stored exact private bytes, validates hash and records grant-specific PDF view evidence. Never regenerate a previously presented PDF from the current catalog/template. Dompdf disables external fetch/PHP/JS; all fields escaped. No public artifact URL/storage link.
- `DecideQuote::execute(PortalContext $client,array $input,string $key): QuoteDecision`; `POST /portal/api/quote/accept` and `/reject`, with outcome derived from the route. Input: expected_revision, snapshot_sha256, pdf_sha256, consent_version, consent_sha256, name (2–255), email, consent=true. Must open this presentation's PDF through this grant first. Admin-authenticated sessions cannot accept/reject for a client. Acceptance is not a legal contract signature, verification of mailbox ownership, payment or resource hold. Both outcomes capture the exact configured consent; UI shows that text verbatim.
- Grant→event→quote locks, current identity/revision/status/validity rechecked. Stale/revoked/expired/superseded/cross-client/modified hashes reject. Same UUID+intent returns the original decision; another UUID with identical decision also returns it without another audit. Changed intent after decision409. Opposing simultaneous decisions yield one winner. No funds, financial revisions or capacity changed by deciding.
- Revising sent/rejected/expired proposals becomes explicit in B; accepted is never revised. Lock owner→existing quote grants (ascending IDs)→event→quote; revoke/clear all previous quote-link ciphertext in the same revision transaction, then create the new revision. Existing event/contract grants remain untouched. Send uses the same ordered protocol; expiry only locks event→quote and does not acquire grants. This avoids an event→grant cycle against portal decisions/revoke.

## C: bind accepted amounts, then use ordinary payments/capacity

- `ConvertAcceptedQuote::execute(User,int,array,string): FinancialRevision`; `POST /admin/api/quotes/{quote}/convert`. Required expected_version, expected_revision, expected_event_version, decision_id. UUID receipt. Only accepted current decision and unchanged source draft/customer/operational selections/time/travel are eligible. No pre-existing finance, money or signed/issued contract on first binding; conflicting existing agreements need reconciliation/CHANGE-A rather than silent supersession.
- Creates immutable `quote_conversions` (unique quote and event, accepted decision/revision and initial finance), plus financial_revisions nullable quote_revision_id and discount snapshot/discount_cents. Exact quoted subtotal, travel, discount, final, odd-cent deposit and service labels/descriptions/characters are copied, not recalculated from current catalog prices. No ledger entry, grant, contract, resource hold or message is created. Conversion has an explicit owner click and never fires from client acceptance.
- Normal RecordZellePayment/Stripe test Checkout and ConfirmPaidCapacity consume that finance afterwards. The latter still requires actual net ledger receipts and all inventory/staff/driver/transfer/short-notice rules. Quote-bound legacy ConfirmCapacity cannot substitute a claimed external receipt: the central engine verifies the linked finance/current net ledger/reference before using its discounted target. It never adds a fake deposit exception to make discounts pass.
- A later source-draft detail/address correction may produce a new financial revision with the *same accepted money* only when customer, selected price IDs/recipes/duration/characters/outfits, party time and travel amount remain unchanged. Existing client-details review/route evidence rules still apply. Current catalog label/price changes cannot reprice it. Changed commercial/operational terms reject for CHANGE-A/requote. Quote acceptance/version history stays immutable.
- Contract commercial snapshot and printed money lines carry visible discount labels/amounts while legal terms remain unchanged. Card3% calculation remains in the existing test Checkout; no Affirm or live charge. Acceptance evidence remains separate from the later contract signature.
