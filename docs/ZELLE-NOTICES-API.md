# PAY-02: client Zelle notices and owner verification

Contract published before implementation, 2026-10-16. This extends the existing sandbox ledger; it does not send messages, access a bank, reserve resources, change legal terms or activate production.

## Services and routes

- `Portal\SubmitZelleNotice::execute(PortalContext $client, array $input, string $key): ZelleNotice`. POST `/portal/api/zelle-notices`, UUID Idempotency-Key. Existing `checkout.create` scope authorizes this payment write (read-only `payments.read` does not); no new grant scope/default required. Admin sessions cannot impersonate a client. Body: required `financial_revision_id`, `amount_cents` (1–100000000, USD cents); optional nullable `reference` (3–255), `payer_name` (120), `sent_at` (explicit offset, no future time), `note` (1000). Submitted details are claims, not bank evidence. Server binds event/customer/grant/IP/device/time; all extra identity/verified/status fields are ignored. Current financial revision and draft event version required for a new notice; same-key replay returns the original even after a later revision/review.
- GET `/portal/api/zelle-notices`, `payments.read`, bounded pagination `page>=1`, `per_page=1..50` (default25): only this event/customer. Each `notice`: id, financial_revision_id, claimed amount/reference/payer/sent_at/note/submitted_at, derived state pending/verified/rejected, verified_amount_cents (only if verified), reviewed_at. Never exposes bank reference, ledger ID, owner review note, IP/device, other customers or grants. POST returns `{notice: ...}` with the same projection.
- `Finance\ReviewZelleNotice::execute(User $actor, int $eventId, int $noticeId, array $input, string $key): ZelleNoticeReview`. POST `/admin/api/events/{event}/zelle-notices/{notice}/review`, UUID Idempotency-Key. Required decision `verified|rejected`, `review_note` (10–2000). For verified, additionally supply **the actual bank evidence** accepted by existing RecordZellePayment: `financial_revision_id` (current), `amount_cents`, `currency=USD`, `reference`, `received_at` explicit offset/not future, `verified_received=true`, optional `note`. Claimed amount/reference are never silently copied; actual amount can differ with the explicit review note. Reject ignores payment fields and creates no receipt. Return `{review, finance}` (owner-only).
- GET `/admin/api/zelle-notices`: pending queue by default; optional state pending/verified/rejected, event_id and bounded pagination. Includes immutable notice and immutable review (owner audit note/actual linked ledger ID), with server metadata hidden. Claude can use it for Dinero/Inicio; no full scans to derive state.

## Integrity and workflow

Both sandbox flags required, environment local/testing/staging only; cookie/CSRF, active owner + confirmed 2FA and existing throttles remain. Notice and review are append-only model records. State is derived from a unique review, not a mutable client flag. Review locks event then notice and reuses RecordZellePayment within the same transaction: receipt, review, audit and idempotency commit/rollback together. Submission locks grant then event, so revocation and current customer binding are checked under the same protocol as other portal writes. Two owners cannot resolve one notice twice. Normalized bank references retain existing global deduplication; a previously manually recorded matching receipt can be linked without crediting it twice. Two notices may refer to one transfer; each must be reviewed, and ledger deduplication still applies. Rejection does not undo a real payment already registered elsewhere.

Stale notices remain in the queue for explicit owner review using the current agreement, with the original claimed revision visible; no silent reassignment or automatic payment. Verified money never reserves capacity or changes contract/signature state. Overpayment remains visible as credit through FinanceSummary. Subsequent correction/refund requires a separate ledger adjustment flow; immutable receipts/reviews are not edited here.
