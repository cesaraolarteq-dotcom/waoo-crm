### B1a: internal preparation first

The first implementation adds the internal `PrepareClientContract` service and a versioned, explicit submission fingerprint. No route, automatic submission hook, signature exemption or screen is enabled in this slice. Existing owner-review guards remain mandatory for signing until B1b implements the full provenance check and HTTP flow. An issued self-service artifact alone must never make `reviewed=true`: that field means an actual current owner review.

Preparation requires the initial native QuickBook financial revision and a genuine owner-verified test receipt. It never interprets an unpaid Stripe lease as payment. An existing issued result can be returned only after rechecking current grant, submission, agreement, customer snapshot and private artifact integrity; it does not renew a grant or regenerate a document. A different UUID with the same current submission returns that one immutable issued document. An unsigned document for an older submission can be superseded, but any signed contract blocks preparation. The audit contains identifiers and hashes, never the submitted personal fields. Artifact failure rolls back the contract/audit/idempotency transaction, preserving the already committed submission; unreachable private artifacts may remain for later authorized garbage collection.

### B1b: HTTP and signature connection, disabled until explicitly configured

`WAOO_SANDBOX_IMMEDIATE_CONTRACTS=false` is an independent rollout gate. With the gate off, existing details response, review path and signing requirements remain; the retry route is unavailable. With the gate on, native paid quick bookings attempt preparation after durable submission and return the additive preparation result. Policy/version/source/scope/template rejection means `review_required`; unexpected PDF/storage/audit failure means `retry_required`, with no private exception text or request logging. `POST /portal/api/details/contract` returns the ready contract or the existing controlled authorization/409/422 response; infrastructure failure returns a generic503. UUID preparation and submission scopes remain separate.

Signing without an owner review is permitted only for the exact B1 issued contract with its closed version1 provenance, latest unchanged same-grant submission, current initial native paid agreement and original owner-approved commercial snapshot. A shared source validator is used at preparation and signature; it never creates a review, payment or inventory allocation. The signature consent, full PDF-open requirement, byte hash and immutable evidence are unchanged. Exact already accepted signature replay remains read-only under the existing access checks. Turning off the gate blocks new self-service signatures; it does not rewrite historical evidence or invalidate a genuine owner-reviewed path.

Portal GET may validate a prepared contract and advance to signature; it never issues a document. For an owner-agreed address and ZIP, the form shows read-only original values; an absent owner address may still be collected but requires review. A saved/unprepared submission offers an explicit retry, with the displayed submission/event versions and a stable retry UUID, without resubmitting details. Signature success advances to pay/done even when owner review is absent. Owner screens retain a distinct unreviewed-details indication alongside issued/signed state; no implied approval. All added nonlegal interface copy is ES/EN. No sends or activation are part of this delivery.

Explicit correction before signing: with the rollout gate on, an unreviewed/unsigned client may choose `GET /portal?review_details=1` to see her saved details against the latest displayed event/submission versions and current read-only agreed address/ZIP/time. GET never stores or prepares. Saving is a new explicit submission (new revision), not a silent retry with newer pins; the script clears review_details before returning to the normal portal. Signed or owner-reviewed flows do not reopen through this query. This also resolves a benign capacity confirmation that changed the event version after a client submitted but before she signed: old signing/preparation still conflicts, and only her explicit refreshed submission can prepare the current unchanged agreement. An actual changed financial agreement remains owner review territory. The address fields explain how to request a change, and payment interface copy refers to recorded payments/balance without promising full staffing or capacity.
