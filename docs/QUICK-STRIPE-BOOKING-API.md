# Quick Stripe booking — sandbox API contract, 2026-10-20

Codex · contract before code · owner decisions `QUICK-STRIPE-BOOKING.md`2af0130. Depends on costume hold V1. **Design only, no endpoint/backend/provider activation delivered by this document.** No real charge/send/deployment, Affirm, HoneyBook event or original-source authority bypass.

## Commercial amount and states

Native CRM bookings only. Owner chooses deposit_percent50(default)|100. Server freezes the agreed services/extras + travel fee minus agreed discounts in one FinancialRevision, USD cents. Principal = ceil(total×percent/100); customer_fee = round-half-up(principal×3/100); payable = principal+customer_fee. Browser amounts are hints, never authoritative. Show all three before paying, same fee for every actually enabled Stripe method. No Stripe surcharge feature or later method-dependent addition. Original service total/deposit-target principal stays separate; receipt keeps real gross, reporting/payment balance credits only verified principal, reports fee separately. Never treat3% as extra package sale or principal credit.

Pending payment uses a separate `quick_stripe_bookings` record and lease-backed inventory group, **not a fake LedgerEntry, owner verification or paid QuickBookingRecord**. The paid hold V1 receipt FK must not be satisfied by a dummy receipt or silently weakened. Introduce explicit versioned unpaid backing in the common inventory protocol; freeze48h created_at/expires_at and24h reminder_at once at durable link/lease creation. Retries, new checkout sessions, reading/copying the link or a reminder never renew the lease.

States: awaiting_payment, processing, deposit_received, expired_unpaid, paid_needs_review, cancelled/review_required. Deposit_received means actual commercial payment received; **staff/equipment/driver capacity is not invented** and Event.status stays draft until existing complete operational confirmation. On verified payment, real gross receipt and principal/fee evidence append once, create/bind the genuine paid quick-book linkage, consume unpaid backing into paid costume hold without duplicate reservation. Same portal continues to details/contract. Do not auto mark capacity_reserved without staff review.

Date/time held is that party's pending operating slot, not exclusive ownership of a whole calendar day or a promise of full crew availability. Staff stays for later. Unknown buffers use known costume window + review_required/timing_unknown, preserving null. No costume recipe means a date/payment lease without fake costume inventory. Failed initial inventory allocation is explicit blocked; do not create a payable promise for unavailable capacity.

## Portal API (proposed, unregistered)

Existing fragment session, same customer/event scope; entry payment step does not require an already signed contract. Scope `quick_booking.pay` grants only this pending agreement, with its versioned snapshot and existing original access expiry/revocation. It must not bypass existing native `checkout.create` contract/finance guards for other payment flows.

- `CreateQuickStripeCheckout::execute(PortalContext,array,string):array`; POST `/portal/api/quick-booking/checkout`, `{expected_booking_version,expected_payment_sha256}`. Returns `{intent_id,status,checkout_url,expires_at,principal_cents,customer_fee_cents,payable_cents,methods}`. Separate purpose/backing discriminator ties intent to this agreement. Fresh scope/authority and immutable actual request parameters checked on retry; no duplicate active provider intent.

Allowed desired methods: card, Klarna, Afterpay, Zip; **never Affirm**. Card/Klarna/Afterpay require real account support; provider key for Afterpay is afterpay_clearpay. **Do not invent a Checkout payment_method_type='zip' if the authenticated Stripe account/SDK does not support it.** Zip is exposed only through a verified supported Stripe integration/capability; otherwise return method_unavailable with owner review, never a fake option or silently pretend it is enabled. No live capability setup or provider terms approval is inferred. Provider descriptions use WP-{event_id}, package and date; do not place full client name/contact in provider metadata/logs merely for a memo. Owner can identify the party by internal reference and portal.

Checkout session may live at most24h, independently of the48h inventory lease. Persist the **exact** provider request including account/origin/amount/method configuration/expiry/idempotency key before network; unknown result retries that same request. Provider expiry = min(lease expiry, now+23h) with a minimum31min creation margin; if too near lease end, refuse a new session instead of silently extending the hold. A later session is allowed only after authenticated closure/no unknown asynchronous payment of the previous attempt, never just elapsed local time. No client return URL marks payment received.

## Webhook, lease expiry, reminder

Extend the existing signature-verified account/test-mode callback processor/router via an explicit quick-stripe intent binding, not metadata alone. Independently retrieve/verify session+PaymentIntent/paid captured charge, amount/currency/account/event/finance. Append one real receipt globally by provider payment identity, immutable gross/principal/fee verification and audit; atomic booking transition+paid hold promotion on current valid stock. Later duplicate/out-of-order callback cannot create another receipt, promote twice or rewrite success as failure. Native/TIP/import namespaces keep their own guards/evidence. Any actual money survives stale authority, missing lease, corrupt state or storage retry, with review rather than guessed credit.

At48h unpaid, release only that lease's inventory, set expired_unpaid, preserve event/customer/agreement/attempt/history, invalidate payment creation and manual reminder. Expire provider sessions idempotently after commit; **local release is not proof remote money cannot arrive**. Existing processing/outcome unknown stays visible for reconciliation, does not silently extend the owner's48h inventory deadline. A late genuine paid callback retains money and atomically attempts current date/costume reacquisition; free → paid hold/deposit_received, unavailable → paid_needs_review, no auto refund or silent assignment to another costume. Terminal cancelled/changed-agreement authority never auto resurrected; actual late money retained for owner review.

At24h and still unpaid, create one durable reminder occurrence with fixed lease/version/source fingerprint. Until MAIL transport + exact owner-approved template are enabled, expose manual WhatsApp/SMS text only; no client send, no sent marker from opening an app. Expired/paid/cancelled/stale source invalidates reminder, no catch-up burst. Future MAIL uses same occurrence and explicit allowlist/provider safeguards; owner approved live sending separately required.
