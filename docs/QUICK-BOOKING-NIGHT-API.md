## 6–7. Optional Zelle reference and receipt day — freeze before code

QuickBook deposit.reference and RecordZellePayment reference become nullable/blank (canonical null); if supplied, retain the existing global case-insensitive bank-reference uniqueness and exact UUID replay semantics. Never invent a bank reference, reuse a different receipt silently, or treat a client notice as a verified payment.

For a missing reference, duplicate protection is event + actual amount/currency + Houston received day, checked under the event lock against all native Zelle receipts, not just other reference-less receipts. A separate fallback identity key derived from that tuple is also unique. Same UUID/exact intent replays the existing result; another UUID that collides asks the owner to review the history. If it is actually a distinct equal-value payment that day, the owner must supply its real bank reference to distinguish it (never a made-up code). Explicit distinct bank references keep the prior supported same-day equal-value flow. This is manual bank evidence, not authenticated bank reconciliation or a guarantee against incorrect human references.

QuickBook additionally checks possible repeat native bookings with the same party window, amount/received day and existing customer or matching exact email/conservatively normalized phone. It does not merge customer records. Reference-less quick creations serialize owner rows in deterministic order before checking committed records, so two owners cannot both create the same reference-less first receipt by racing new customer/event IDs. A match rejects/rolls back the new attempt and points to history; original money/event remains untouched. No imported/HoneyBook receipts are fabricated or rewritten.

Both services accept optional received_on (YYYY-MM-DD, Houston) instead of received_at, mutually exclusive; the old explicit-offset received_at API stays supported. Validate the local day, pin the day (not now) in the idempotency request hash, derive the actual receipt timestamp only inside the first successful transaction after the replay check: now/startOfSecond for today;12:00 Houston for an earlier day. Reject future days. This lets response-lost retries use the same exact intent without a new moving timestamp. QuickBook forwards the day to RecordZellePayment.

Owner quick form removes deposit time and DST occurrence controls, keeps received date (default Houston today), and sends received_on only; no hidden editable bank time. Existing API callers can still send received_at. No fake exact bank observation claimed: the timestamp is a system/date convention selected by the owner for a manually verified receipt. Financial and QuickBook request hash changes are versioned behavior; historical explicit-timestamp replay still uses its original input.
