# BOOK-QUICK — implementation contract for Claude

2026-10-15 America/Chicago · `codex/quick-booking-core`. **Published before the implementation in this increment.** Extends DOC-PAY-API and the accepted QUICK-BOOKING-API-DECISIONS. These routes/classes are planned until the tested delivery entry marks them implemented. No deployment, real charge, outbound message or owner acceptance is authorized by this document.

## Owner half

`Booking\QuickBook::execute(User $actor, array $input, string $key): Booking\QuickBooking` and owner POST `/admin/api/quick-bookings` with Idempotency-Key. Same input Claude's QuickBooking page already produces: exactly one of `customer_id` or `new_customer`, SaveEventDraft event/service/character fields, explicit `event_type`, non-null known `travel_fee_cents`, `deposit {method:zelle,amount_cents,reference,received_at,verified_received:true,note?}`, `portal {expires_at}` optional (default 14 days; max 30 days).

Both sandbox flags must be enabled in local/testing/staging, production denied. Fresh owner/2FA authorization. Required fields/rules delegate to existing services; no invented catalog or price. Customer + event + immutable financial revision + actual verified Zelle ledger + quick-booking row + payload-bound mutation receipt commit together. The customer/event cannot be duplicated by concurrent same-key retries. Invalid core input/duplicate reference/audit failure rolls back this whole core transaction. Grant issuance runs after that commit; failure leaves the money/event plus `portal_link_pending` owner exception. No external charge occurs.

Result DTO public properties: `id`, `event`, `customer`, `financial_revision`, `receipt`, `finance`, `portal_url`, `portal_expires_at`, `portal_link_already_shown`, `link_issue_pending`. Raw link returned once only, never stored in quick-booking/mutation/audit records. Replays return `portal_url:null` and preserve all original records; if grant creation failed they also return `link_issue_pending:true`. Do not show "nothing saved" or thank the client with an empty link. Owner can issue a replacement grant through existing POST `/admin/api/events/{event}/portal-grants`; same event/receipt remain. No resource reservation/availability promise is made by QuickBook. Wording must distinguish a saved deposit/booking request from assigned resources.

`quick_bookings` binds creator/event/customer/initial financial revision/receipt, grant ID nullable and requested expiry. Grant issue failure is recoverable, not another deposit. UUID key is scoped to owner + operation, canonical payload hash; customer/event references are server resolved.

## Client details

Add `details.submit` to the allowed grant scopes (max five); existing default four-scope grants remain unchanged. QuickBook requests all five. Portal GET `/portal/api/event` adds `details` for the holder of details.submit: `{submission: {id,revision,data,submitted_at}|null, reviewed:bool, expected_revision:int, expected_event_version:int}`. Other scopes do not expose details. Portal POST `/portal/api/details`, Idempotency-Key, delegates to `Portal\SubmitClientDetails::execute(PortalContext $client,array $input,string $key): ClientDetailsSubmission`.

Body: `expected_revision` required integer >=0 (0 for first); `first_name,last_name,phone,email,billing_address,event_address` required, optional `event_postal_code` (ZIP/ZIP+4), optional `locale` es/en; `start_time_confirmed` required boolean; when false, `requested_start_at` required date with explicit offset. Optional `child_name`, `child_age` integer 0–120, `theme`, `notes`; `sms_consent` optional boolean and `sms_consent_version` when true. Name fields max120, addresses255, phone40, email255, notes2000, child/theme120. No browser-supplied IP, user-agent, signer identity, server time, prices, event customer ID, staff IDs or approval flags are trusted.

Store an immutable numbered submission, base customer snapshot, grant provenance and server request IP/device/time; audit as client source, not owner. No mutation of customer/event dates, services, money or resources. Same key/payload returns the same submission even after subsequent approval/signature. Different payload/key with stale expected_revision returns409. After a signed contract, new submission requires CHANGE-A (409). Admin sessions cannot impersonate the client. Expired/revoked/wrong-event/customer or insufficient scope fails closed. SMS true is accepted only with an explicitly configured approved text/version; default configuration has none, so false/omitted works and no SMS enrollment/send occurs. Consent text/hash/time is pinned, not inferred from a checkbox alone.

`client_details_submissions` is immutable and unique (event,revision). `client_details_reviews` is immutable and unique per submission. Client response omits IP/device, base customer history and owner/internal audit. Latest unreviewed submission prevents signature/contract issuance for that quick booking, so an old PDF cannot be signed as though newer details were approved.

## Owner review and contract bridge

GET `/admin/api/events/{event}/client-details` lists submissions with review status, latest first (owner only). POST `/admin/api/events/{event}/client-details/{submission}/approve`, Idempotency-Key → `Booking\ApproveClientDetails::execute(User $actor,int $eventId,int $submissionId,array $input,string $key): ClientDetailsReview`.

Body `{expected_event_version,expected_revision,travel_fee_confirmed:true,review_note,requested_start_resolution?}`. `review_note` min10/max2000. If start_time_confirmed=false, only `requested_start_resolution:"keep_original"` is supported here, with explicit owner note confirming the discussion; rescheduling remains future CHANGE-A. This endpoint never moves a party or changes travel fee/package amount. Owner must verify proposed address/ZIP and confirm the existing quoted transportation amount still applies. Otherwise use a separately reviewed change/requote, not a silent portal adjustment.

Under event then customer/variant locks, reject stale submission/event/contact snapshot, non-draft/reserved event, any signed contract or changed service recipe. Reuse SaveCustomer and SaveEventDraft for approved name/contact/venue, preserve original time, prices, character choices and financial amounts; create a new financial revision because event version changed, keep ledger once at event level, supersede prior unsigned contracts. Store review/financial linkage/audit in the same transaction. Failures leave all original data, agreements and received money intact. No guessed address/price/character or automatic routing.

After approval, owner may call the existing CreateContract/IssueContract with the latest financial revision and explicit adult billing identity. A current unreviewed submission blocks issue/sign; only approved details matching the contract's financial revision are eligible. Manual non-quick bookings with no details submission retain existing DOC/PAY behavior. No automatic issuance/activation of legal text, countersignature, email or message.

## Attention cards

Owner GET `/admin/api/quick-bookings?state=waiting_details|review_details|ready_to_issue|waiting_signature|signed` (paginated; optional state). Derived state: signed contract → signed; latest submission not reviewed → review_details; current issued contract → waiting_signature; reviewed latest submission → ready_to_issue; otherwise waiting_details. Return event/customer IDs/title, receipt/finance IDs, grant/link readiness, latest submission/review and separate capacity/payment/contract states; no raw token. `ready_to_issue` additionally requires current review financial/event agreement linkage; stale changes return review_details rather than imply readiness. Link recovery comes from grant/expiry/revocation plus pending exception, never hides real money.
