## Six trusted business occurrences

CaptureMailOccurrence::record(string $key, int|string $sourceId, array $locator, ?User $actor=null): ?MailOccurrence is internal only. It runs inside the existing domain transaction, emits IDs/versions only and never calls a provider or queues a body/recipient/token. Disabled mail creates no occurrences and activation never backfills old business events. Unique identity = key + immutable business subject/revision, not browser retry key. Business rollback rolls back the occurrence; same request replay cannot create a second one.

| key | authoritative source and automatic hook | required fresh checks |
| --- | --- | --- |
| inquiry_received | newly committed ReceiveWebsiteLead LeadSubmission/Lead | exact submission, valid source email/locale, not lost/booked; no customer/event/finance creation |
| quote_sent | SendQuote prepared QuotePresentation + exact revision/grant | current open sent quote, exact immutable PDF/snapshot/consent, matching customer/version, active quote grant |
| details_request | IssuePortalGrant for an existing QuickBookingRecord with details.submit | actual pending client details, matching finance/customer, live grant; not merely an arbitrary event link |
| contract_ready | issued Contract when an active suitable event grant exists, or IssuePortalGrant after issue | latest issued unsigned contract, approved source template, current finance/customer, contract.read/sign scopes; never invent a signature or issue a link automatically |
| payment_received | newly created verified test LedgerEntry receipt (owner_verified or verified_stripe_webhook) | actual receipt and agreement, current customer, real received amount; never an imported or pending Zelle claim |
| zelle_notice_pending | newly committed SubmitZelleNotice | same still-unreviewed notice and agreement, live original grant; amount explicitly a claim, never verified credit |

Link-dependent notices wait for an explicitly issued appropriate grant before capture; no auto issuance/renewal/rotation. Sources with missing links/configuration/email are reported as skipped/blocked; no historical automatic resend when configuration or links later change. An explicit future resend contract is separate. Contract-ready deduplicates by issued contract revision; details request by quick-booking record; quote by quote revision; receipt/notice/lead by immutable source id.

## Persistence and processing

Migration370000: immutable mail_occurrences (key, subject identity/revision, nullable event/customer/lead/actor references, encrypted locator, unique dedupe hash, occurred_at); mutable mail_occurrence_states (pending/materialized/skipped/blocked, version, fixed reason, optional outbound id). OutboundMessage gains nullable event/customer/financial/creator references and source occurrence id, because a lead or quote has no verified money or customer/event in some cases. Never fabricate those domain rows. Existing reminders retain their original nonnull bindings and behavior.

MaterializeMailOccurrence::execute(int $id): ?OutboundMessage re-locks the authoritative source before the occurrence state, validates the binding and template, renders approved copy, and creates one encrypted immutable OutboundMessage plus its scheduled state atomically. waoo:mail:materialize --limit=100 polls pending IDs only; subsequent dispatch uses the existing claim-before-transport and unknown-result/no-resend protocol. Missing approval stays visible as blocked, no fake send; retries cannot retarget an existing immutable envelope. A fresh source re-render must match the frozen source/template/body before dispatch. Address/contact/revision/paid-state changes invalidate stale notices; ordinary capacity linking may keep the same current financial agreement. Event pause and sandbox owner allow-list/bounce suppression still apply. Instant notices are scheduled for their occurrence time and retain the existing same-Houston-day dispatch freshness rule.

Lock order: optional portal grant → source event (or lead) → quote/contract/financial source → customer → occurrence/state → event message policy/outbound state. Domain hooks only insert a new uniquely keyed occurrence; they never lock a previously captured occurrence in reverse. Database retry/uniqueness keeps concurrent capture/materialization idempotent. All new jobs carry an integer occurrence/message id only.

## Postmark authenticated bounce adapter

POST /webhooks/postmark/bounces: stateless, no session/CSRF, bounded64KiB JSON, HTTPS mandatory, independent disabled-by-default sandbox flag. Authenticate native HTTP Basic Auth using configured dedicated username/password before JSON parsing; require configured strong secret, constant-time comparisons and never log Authorization or body. No invented signature header. Scope this adapter to Postmark Bounce and SpamComplaint records, configured expected ServerID + MessageStream, exact provider message id and recipient hash belonging to a recorded postmark send. Do not accept another provider or make an unknown message look delivered.

Normalize only provider record ID, MessageID, outcome, BouncedAt and recipient hash; check timestamp is explicit/valid and at most five minutes ahead of receipt time, recipient matches encrypted intent, and provider binding exists. Preserve the provider timestamp (do not clamp it to now); only the authenticated adapter permits this bounded clock skew. Internal generic delivery events keep their existing no-future rule.

2026-10-19 classification amendment, before implementation: Postmark Bounce requires nonempty `Type` (max80 chars); optional `Inactive` must be a JSON boolean. `SpamComplaint` (RecordType or Type) means complained. `HardBounce`, `BadEmailAddress`, `ManuallyDeactivated`, or `Inactive:true` mean bounced. All other types (including SoftBounce, Transient, AutoResponder, DnsError and unknown future types) are non-blocking `provider_notice` evidence: never change message status/version/delivered_at, never suppress a recipient, never schedule retries. Missing Type is422, not a guessed permanent failure. Normalized evidence includes the bounded provider type and inactive flag; no raw body, description or recipient. Same provider ID with changed type/inactive/time/message/outcome is409. Duplicate exact notice returns200. A late transient notice never clears a previous bounce/complaint.

The provider-neutral RecordMailDelivery seam gains `authenticatedObservation(provider,messageId,eventId,outcome,occurredAt,evidence)` for an authenticated disabled adapter; only bounced/complained/provider_notice are allowed and future tolerance is five minutes. Generic execute and suppression policy stay provider-neutral. Postmark remains an optional sandbox adapter, **not an owner-selected provider**. No DNS/account configuration follows from this amendment. RecordMailDelivery preserves append-only idempotent evidence and suppression; complaint/bounce outranks delivery. A duplicate exact record returns200; conflicting id409; unknown/early send mapping503 (retryable), bad authentication401, disabled404, malformed/unsupported422, oversized413. Responses and persistence do not echo/store raw email/body/headers. Handler must not change financial, event or portal state. Credentials stay in environment settings, never source files/chat.

Protocol reference: https://postmarkapp.com/developer/webhooks/webhooks-overview and bounce-webhook/spam-complaint-webhook. Current environment returns403 for official documentation, so live provider configuration/authentication verification remains an explicit preactivation requirement. A concrete native Basic Auth adapter can be tested with synthetic HTTP requests; no claim of a live Postmark integration or selected/activated provider is made.
